    Build plan

    Effort is estimated full-time weeks for one experienced developer, from 04-feasibility.md. It isn't tested, and there are no dates because this is a free-time project.

    Parallel work only saves time with more than one person, such as contributors. Working alone, the tracks are an order you can choose freely, not a shortcut. The people figure above also ignores coordination time.

    Order to start

    1. Build the prototype (M0), to prove the terminal tab, keys, session resume and memory on all three systems before investing further.
    2. Build the core, in order and ideally with one person, because everything else plugs into it.
    3. Pass the core gate, which freezes how the other work connects to the core.
    4. Start the parallel tracks. If working alone, I'd suggest D, A, F, E, C, then B: the terminal, AI sessions and projects make this editor different.
    5. Release the first version, then build language servers and later Git, then plugins, then the store.

          Core gate: what must be stable before parallel work starts

          Proposed. If these hold, tracks can be built without touching each other's code:

          • A message channel for sending results to the UI loop
          • A tab interface that both file tabs and terminal tabs can use
          • A panel view interface, so that any view fits either panel
          • Read access to the active project and directory
          • Registration for commands and key bindings
          • Config loading and validation
          • A trust check that any feature can call
